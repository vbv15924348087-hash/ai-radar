# AI Agent 开始替商家做事，产品经理该怎样设计“可控执行”？

**摘要：**Meta 给小企业的 Muse 增加了经营工具连接器，并承诺发布、发送和支出前取得用户批准；Codex CLI 新增可选的执行中即时转向；Qwen Code 则在版本日志中继续建设工作区和会话恢复能力。这三条更新指向同一个产品问题：当 Agent 可以跨工具持续工作时，用户怎样知道它被允许做什么、正在做什么，以及中途改口后哪些动作已经发生？本文用一个假设的商家任务，提出授权、确认、转向和恢复的设计方法。

一家小店准备周末促销。店主对 AI 助手说：“看看最近卖得好的商品，做一条 Instagram 宣传内容，再通知店员准备库存。”

这句话听起来是一个任务，执行时却可能跨越销售数据、库存、设计素材、社交账号和团队消息。助手读错库存，会写出无法兑现的活动；把草稿当成正式内容发布，会影响顾客；店主在执行中改了折扣，也可能留下两版互相冲突的通知。

因此，产品经理要解决的核心问题不是“Agent 能连多少工具”，而是**一次授权究竟允许它做哪些动作，每个动作如何被确认、改变和追溯**。

9 月 29 日的几条官方更新让这个问题更具体。Meta 为 Muse for Small Business 增加了 Asana、Canva、QuickBooks、Shopify、Slack、Stripe 等连接器，并明确表示，发布、发送或支出之前需要用户批准。[1] OpenAI 在 Codex CLI 0.159.0 中加入可选的 `instant_interrupt`，允许用户在模型回复或长时间调用期间输入新要求。[2] Qwen Code 0.24.7 的版本日志则出现了可选 Worktree、结构化按需记忆召回和托管工作区在可信本地重启后的恢复等变更。[3]

三者的适用场景不同，也没有组成一个现成的联合产品。它们可以作为观察窗口：Agent 一旦进入持续执行阶段，控制权必须贯穿任务开始、动作发生和任务恢复，而不能只放在开始时的一次“允许”。

## 一、先把一句需求拆成可授权的动作

对“做周末促销”这样的请求，直接弹出“是否允许助手访问所有工具”，用户很难判断风险。更有用的做法是先拆动作，再为每一类动作定义权限。

| 动作 | 商家任务中的例子 | 建议的产品处理 |
| --- | --- | --- |
| 读取 | 查看近 30 天销量和当前库存 | 说明数据来源、范围和使用目的；只授予完成本次任务所需的读取权限 |
| 生成草稿 | 起草文案、海报和店员消息 | 允许自动生成，但标明草稿版本和所依据的数据 |
| 修改内部状态 | 创建待办、调整内部排班 | 展示具体改动和影响对象；必要时要求确认 |
| 对外发送或发布 | 发 Instagram 内容、给店员群发消息 | 在执行前展示最终内容、收件人或渠道，并取得针对该动作的批准 |
| 支出或承诺 | 购买广告、下单补货、给出优惠承诺 | 展示金额、上限、付款账户和不可撤销后果，单独批准 |

这张表是本文提出的设计建议，不是 Meta 公布的权限分级。Meta 的明确承诺是发布、发送和支出前取得批准；至于每种连接器的细粒度权限、审批界面和回滚能力，需要以实际产品为准。[1]

一个可执行的任务授权，至少应记录四件事：目标是什么；允许读取哪些数据；允许生成哪些草稿；哪些动作必须停下来等人确认。预算、有效期和可操作对象也应写入授权范围。用户说“帮我准备活动”，并不等于允许系统“替我花钱投广告”。

## 二、审批要确认“这一次动作”，而不是再次确认整段对话

很多审批界面只给出“继续”或“取消”。这对低风险草稿足够，对发布和付款却太模糊。用户应当看见将要发生的具体动作：

> **待确认：发布周末促销帖**  
> 渠道：某 Instagram 商业账号  
> 内容：海报第 3 版、文案第 2 版  
> 依据：截至今天 16:00 的库存数据  
> 承诺：指定商品八折，活动截止周日 22:00  
> 执行方式：批准后发布一次；内容变化需重新确认

这是界面示例，不是 Muse 的真实截图。它把用户真正要承担的后果放在确认按钮旁边。

审批还要绑定一个明确的动作版本。如果文案、折扣、目标账号或金额在审批后变化，旧批准应失效。对外调用则需要唯一执行编号，防止网络超时后重试两次、发出两条帖文或重复扣费。无法保证幂等的外部工具，应在重试前先查询上一次执行结果。

这里有一条容易漏掉的产品规则：**“用户批准了计划”不能自动等同于“用户批准了计划里所有未来的具体动作”。**计划只是意图；外部动作发生前，还应核对实际参数是否落在授权范围内。

## 三、用户中途改口，系统要交代旧动作到了哪一步

假设店主看着生成过程，又补充：“折扣改为九折，先别发帖。”此时回复“好的”不够。系统至少要知道：海报是否还在生成，消息是否已发送，发布请求是否已提交，付款是否已经发生。

Codex CLI 的 `instant_interrupt` 展示了执行中接收新输入的交互方向，但该功能是可选的，也不能据此推断已启动的外部动作会自动撤销。[2] 产品设计需要把“新要求已收到”和“新要求已应用”分成两个状态。

对商家来说，状态反馈可以写得很直白：

> 已收到“改为九折、暂不发布”。当前海报仍在生成，Instagram 尚未收到发布请求；店员消息草稿已作废。系统将用九折重新生成文案，完成后再次请你确认。

如果发布请求已经发出，反馈也必须如实变化：“发布请求已提交，正在查询平台结果；在确认结果前不会重复提交。”用户要的是后果清单，而不是一条看似顺从的聊天回复。

实现上，可以为任务和外部动作分别保存状态：`待执行 → 执行中 → 等待确认 → 已提交 → 已确认成功/失败/结果未知`。中途改要求时，新版本只接管尚未发生的动作；已发生的动作进入查询、撤回或补救流程。对于“结果未知”，系统不能简单地按失败重试。

## 四、任务跨天或重启，恢复的不只是聊天记录

促销任务可能做了一半就遇到断网、进程重启或人离开电脑。Qwen Code 0.24.7 的版本日志把可选 Worktree、结构化记忆和托管工作区恢复列入变更，说明持续会话正在成为 Coding Agent 的建设方向。[3] 其中不少 Hosted、managed 能力带有受限或内部阶段标记，不能把它们描述成所有普通用户都已默认可用。

对经营 Agent 而言，真正需要恢复的是可核对的任务状态：确认过的目标版本、每项授权的范围和有效期、已经完成的外部动作、未完成的审批、外部平台返回的执行编号，以及下一步该做什么。只恢复一段聊天文本，无法可靠判断“那条帖子究竟发出去了没有”。

一个实用的恢复页面可以把任务拆成三栏：**已完成且有回执、等待你确认、结果待核实**。只有第三栏核实之后，才能决定重试或补救。工作区和记忆有助于继续工作，但它们不能替代外部系统的真实回执。

## 五、验收 Agent，不要只看“能否把任务做完”

如果团队准备上线类似能力，建议用真实业务流程做一次端到端验收，至少检查以下问题：

- 用户只授权读取库存时，Agent 能否被阻止发布内容或支出？
- 发布前的确认页能否展示最终内容、目标账号和关键承诺？确认后改了折扣，旧批准是否失效？
- 外部接口超时后，系统能否先查执行结果，再决定是否重试？
- 用户中途改要求时，界面能否区分“已收到”和“已应用”，并列出旧动作的状态？
- 服务重启后，能否恢复审批、执行编号和结果未知项，而不重复发帖或扣费？

指标也应覆盖后果：任务完成率、用户审批耗时、审批后修改率、误发与重复执行次数、结果未知的核实时间，以及每个合格任务的总成本。单看工具调用成功率，容易掩盖用户最后仍需人工收尾的问题。

Meta Muse 目前面向美国和加拿大；本文讨论的是可以迁移到其他 Agent 产品的设计方法，而非已在国内平台验证过的上线结果。示例商家、界面和验收规则均为假设方案。Agent 能连接更多工具后，产品真正需要交付的是一条用户看得懂、改得动、查得到后果的执行链。
